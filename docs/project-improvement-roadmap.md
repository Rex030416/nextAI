# 多格式文档智能问答系统：改进路线图

> 本文只记录当前仓库**尚未实现**、**尚未接入运行链路**或需要补强的能力。用于后续按优先级推进，避免把设计稿、基础设施和已上线功能混在一起。

> 更新（2026-07）：`backend/` 已完成 Java 21 + Spring Boot + Spring AI 的第一阶段工程化替代，上传返回 `documentId`、MinIO 原始文件持久化、异步 Tika 解析、pgvector 入库、owner/document 过滤、向量 + 关键词 RRF 检索、对话记忆与 pgvector 语义缓存，以及 React TypeScript API 接入。详情见 `docs/engineering-refactor-2026-07.md`。以下 P0/P1 条目保留为验收和后续完善清单，其中认证、可靠消息队列与 Redis 精确缓存仍未完成。

## 1. 当前实际能力

当前运行链路为：

```text
前端上传文件
→ Express /upload 保存到本地 uploads/
→ 前端发送问题到 /chat
→ Unstructured 解析文档
→ 段落优先的文本切分
→ OpenAI Embedding
→ 临时创建 FAISS 索引
→ FAISS 语义召回 Top 20 + 本地 BM25 关键词召回 Top 20
→ RRF 融合为 Top 4
→ GPT-3.5-turbo 回答
→ 前端显示纯文本问答
```

当前已经创建、但尚未接入业务运行链路的基础设施：

- `docker-compose.yml`：PostgreSQL + pgvector 容器配置。
- `server/db/init.sql`：`documents`、`document_chunks`、HNSW、GIN 关键词索引及 32 个 `owner_id` 哈希分区。
- `server/.env.example`：数据库连接示例。

## 2. P0：正确性、隔离与基础 API 改造

### 2.1 文档身份替代全局 `filePath`

现状：后端将最后一次上传文件路径保存在全局变量 `filePath`；所有用户、所有请求都会覆盖该值。

改进：

```text
上传成功
→ 生成 documentId
→ 返回 documentId 给前端
→ 前端问题请求携带 documentId
→ 后端只处理该 documentId 对应的文件和索引
```

验收标准：并发上传两份不同文档后，分别提问不会串文件。

### 2.2 用户身份与访问控制

现状：没有登录、`userId`、`owner_id` 写入和权限校验。

改进：

- 接入认证机制；开发期可使用 mock user，生产环境使用 Session 或 JWT。
- 上传时记录 `owner_id`。
- 所有读写、检索、删除操作强制校验 `owner_id`。
- 查询必须限定 `owner_id + documentId`。

验收标准：用户 A 无法读取、检索或删除用户 B 的文档。

### 2.3 文件上传与错误处理

现状：没有文件类型、大小、病毒/恶意文件限制；`/chat`、解析和模型调用缺少统一错误处理。

改进：

- 白名单允许 PDF、DOCX 等已验证解析格式。
- 限制文件大小、页数和解析时长。
- 创建 `uploads/` 目录并使用唯一文件名，避免同名文件覆盖。
- 对上传、解析、Embedding、检索和模型调用返回统一错误码。

## 3. P1：持久化文档索引与异步入库

### 3.1 接入 PostgreSQL + pgvector

目标：将当前“每次问题都创建临时 FAISS”的流程改为“上传时索引一次，提问时直接查询”。

目标流程：

```text
上传文档
→ 创建 documents 记录，状态为 indexing
→ 解析、段落切分、生成 Embedding
→ 写入 document_chunks
→ 创建或更新关键词字段
→ 状态更新为 ready

用户提问
→ 按 owner_id + documentId 读取已存在的 chunk
→ 向量检索 + 关键词检索
→ 生成答案
```

实现项：

- 增加 PostgreSQL 客户端与数据库访问层。
- 将 `documents` / `document_chunks` 的 schema 接入上传和聊天 API。
- 使用 `VECTOR(1536)` 保存当前 Embedding；记录模型名称和维度，方便未来迁移。
- 使用 HNSW 向量索引与 GIN 关键词索引。
- 使用 32 个 `owner_id` 哈希分区；所有查询必须带 `owner_id` 才能触发分区裁剪。

验收标准：服务重启后，已上传文件仍可问答；重复提问不再重新解析整份文件和生成全部文档 Embedding。

### 3.2 异步索引 Worker

现状：上传、解析、Embedding 和问答尚未分离。

改进：

```text
API 接收上传
→ 保存原始文件
→ 投递索引任务
→ Worker 解析、切块、批量 Embedding、入库
→ 前端轮询或订阅 indexing / ready / failed 状态
```

候选技术：BullMQ + Redis（本地/中小规模）或 SQS（云环境）。

验收标准：大文件入库时，上传接口快速返回；用户可看到索引进度和失败原因。

### 3.3 原始文件存储

现状：开发环境已接入 MinIO，原始文件保存至 `nextai-documents` bucket；数据库只记录对象键。

改进：

- 生产环境迁移到 S3 或同类对象存储，并使用独立服务账号与密钥管理。
- 扩充版本、媒体类型、大小和上传时间等对象元数据。
- 实现删除补偿：文件删除与 `documents`、`document_chunks` 数据保持一致。

## 4. P2：检索质量与性能

### 4.1 正确的向量索引策略

现状：chunk 数量达到 50 时尝试使用 `IndexIVFFlat`。该阈值过低，且 IVF 需要足够训练样本和参数调优。

改进：

- 文档量较小时使用精确检索或 pgvector HNSW。
- 文档量增长后，基于离线评测选择 HNSW / IVFFlat。
- 记录 P50/P95 延迟、Recall@K、MRR，不以主观感觉选择参数。
- 不同 `ef_search`、`nprobe` 参数必须在固定测试集上比较速度和召回率。

### 4.2 混合检索入库化

现状：BM25 在每次提问时遍历所有 chunk 并重新计算分数。

改进：

- 将关键词 token、倒排索引或 PostgreSQL 全文检索字段在入库时建立。
- 向量检索和关键词检索各取候选，再使用 RRF 融合。
- 后续可加入 reranker，对 RRF 候选进行精排。

验收标准：检索请求不再遍历和重新分词整个文档集合。

### 4.3 Redis 缓存

缓存不应由前端直接访问，而由后端 API 管理。

优先缓存：

```text
1. 精确问题答案缓存
2. 热门问题的检索 chunk ID / 分数
3. 文档元数据和索引状态
4. 可选：问题 Embedding
```

建议 Key：

```text
answer:{userId}:{documentId}:{documentVersion}:{promptVersion}:{questionHash}
```

缓存失效策略：文档重新上传、编辑、删除或重新索引时递增 `documentVersion`；旧缓存自然失效或主动删除。

### 4.4 语义缓存

目标：当用户用不同表达提出同一问题时，复用已有结果。

流程：

```text
问题基础标准化
→ 精确缓存未命中
→ 生成问题 Embedding
→ 在语义缓存中检索相似问题
→ 仅在 userId、documentId、documentVersion、权限、模型和语言均一致时复用
```

注意：语义相似不等于答案相同；日期、数字、否定词、实体和权限范围必须额外校验。相似度阈值需要通过真实问题集测试确定。

## 5. P3：可扩展部署与观测

### 5.1 无状态 API 与负载均衡

前提：移除全局 `filePath`、本地会话和内存索引依赖。

目标部署：

```text
React 前端
→ Nginx / Load Balancer
→ 多个 Node.js API 实例
→ PostgreSQL + pgvector / Redis / 对象存储 / Worker
```

负载均衡只能分摊 API 请求；解析、Embedding 等长耗时工作应交给 Worker。

### 5.2 监控与评测

需要采集：

- 上传成功率、解析失败率、索引耗时。
- 缓存命中率。
- 检索 P50/P95 延迟、GPT 调用耗时和成本。
- Recall@K、答案引用正确率、无答案拒答率。
- API 实例 CPU、内存、QPS、错误率。

只有具备优化前后的同口径数据，才能在简历中使用“延迟下降 80%”或“负载降低 60%”等指标。

## 6. P4：可信 AI 与隐私保护

### 6.1 提示注入防护

现状：尚未实现输入清洗、检测、指令/数据隔离和输出校验。

目标三层：

```text
第一层：清洗与规范化
  - 不可见字符、Unicode 混淆、编码内容和异常长度处理。

第二层：提示注入检测
  - 对用户问题和解析后的文档 chunk 做规则检测与语义风险分类。
  - 高风险 chunk 隔离，不进入普通检索结果。

第三层：指令与数据隔离
  - System 指令、用户问题、PDF 内容使用独立消息和结构化字段。
  - 文档被明确标记为 untrusted data，只能引用，不能执行其指令。
  - 工具调用必须经过后端权限和参数校验。
```

补充：对模型输出做安全检查；绝不将模型输出直接交给 Shell、SQL、文件路径或高权限工具执行。

### 6.2 PII 脱敏

目标：

```text
原始文档
→ 解析
→ 正则识别手机号、邮箱、身份证等
→ NER 识别姓名、地址、组织等上下文实体
→ 生成脱敏副本
→ 向量入库与送模型前再次检查
```

原始文件应保留在权限受控位置；向量库和模型上下文默认使用脱敏副本。

### 6.3 安全评测

建立包含正常文档、直接提示注入、间接提示注入、编码混淆和 PII 的测试集。

指标至少包括：

- 攻击拦截率。
- 正常文档误杀率。
- 攻击绕过后是否影响回答或工具调用。
- PII 识别率和误脱敏率。

没有攻击样本数、基线与评测脚本时，不应声称“拦截率提升至 93%”。

## 7. P5：AI 文档研读与审阅工作台

产品定位从“PDF 问答”升级为“多格式文档研读、问答与审阅工作台”。

### 7.1 PDF 阅读与批注

- PDF 预览、页码定位、搜索。
- 高亮、下划线、便签、评论、手写批注。
- 批注与 `documentId`、页码、坐标、选中文本绑定并持久化。
- AI 可回答“总结我标黄的部分”“根据这些批注列出待修改事项”。

### 7.2 文档编辑与版本管理

- 区分批注、修改建议、真正修改原 PDF 内容和不可逆脱敏（Redaction）。
- AI 先生成“修改建议 / diff”，由用户确认后应用。
- 保存文档版本、修改人、修改时间与修改记录。
- 真正修改复杂 PDF 排版、扫描件或表格成本较高，应在批注能力稳定后再做。

### 7.3 引用与可信回答

- 每个回答返回文件名、页码、chunk 原文和引用链接。
- 没有足够证据时明确拒答，而不是补全猜测。
- 支持用户对答案“有帮助 / 无帮助”反馈，形成评测数据。

## 8. 推荐实施顺序

```text
阶段 1：documentId、用户隔离、文件校验和错误处理
阶段 2：PostgreSQL + pgvector 实际接入，上传时异步索引
阶段 3：Redis、关键词索引入库化和对象删除补偿
阶段 4：无状态 API、多实例、负载均衡和监控
阶段 5：提示注入、PII 脱敏和安全评测
阶段 6：PDF 阅读、批注、笔记、引用和版本管理
阶段 7：AI 修改建议与受控的文档编辑能力
```

## 9. 近期最小可行目标

下一次实现建议只完成以下闭环：

```text
登录用户上传一份 PDF
→ 返回 documentId 和 indexing 状态
→ Worker 完成解析、切块和 pgvector 入库
→ 用户基于 documentId 提问
→ 从持久化向量库检索并返回带页码引用的答案
```

这个闭环完成后，才适合继续做缓存、语义缓存、负载均衡和 PDF 批注。
